# @autonoma/diffs

AI agents that drive the diff-analysis, healing, and review pipeline. Every agent is a subclass of `Agent` from `@autonoma/ai`, built on the same abstraction: an immutable agent class holds tools + system prompt, each call constructs a fresh `AgentLoop` subclass that carries the per-run state.

**Every model call in this package goes through a `@autonoma/ai` abstraction** - `Agent`/`AgentLoop` for the tool loops, `TextGenerator` for the one-shot vision reads, `ObjectGenerator` for structured output. The AI SDK is a `devDependency` only, because the test harness mocks the model interface itself (`MockLanguageModelV3` from `ai/test`); production code never imports it, and the message types the agents build prompts with are re-exported from `@autonoma/ai`. Adding a bare `generateText` call here is a regression - if the abstraction you need does not exist yet, add it to `@autonoma/ai` (that is exactly why `TextGenerator` exists).

| -------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DiffsAgent`         | PR diffs                  | Which existing tests might be affected; and authors any missing tests directly via `create_test` (mints the test case + plan + a pending generation, with a required coverage justification)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `HealingAgent`       | Refinement loop iteration | What to do about each plan that failed this iteration (update_plan / report_bug / report_engine_limitation / report_unknown_issue / report_scenario_unsupported / remove_test). `report_bug` requires a re-grounded `suspectedCause` (explanation + `file:line` code references, each with an optional verbatim `snippet` from the agent's bash read); when the cause can't be grounded it downgrades to `report_unknown_issue` (Issue without a customer-facing Bug). `report_bug` also authors the customer-facing `report` (Expected/Actual + narrative, plus an optional `primaryScreenshot` designating the frame that best shows the bug - referenced by fetched step + before/after, resolved to a storage key by the tool) the bug page renders, grounded in evidence the agent pulls on demand via `fetch_step_evidence`; the narrative embeds specific screenshots inline by `evidence:<assetId>` token, anchored to a system-built `evidenceManifest` of only the assets the agent actually fetched (so it can never surface an image it did not pull). It only heals and culls - it never authors tests |
| `GenerationReviewer` | Every generation          | Verdict (success / plan_mismatch / agent_limitation / application_bug / unknown_issue / scenario_unsupported). `application_bug` requires a `suspectedCause` grounding the bug in code; ungroundable suspicions are `unknown_issue`; a test impossible given the current scenario data (with a description anchoring intent) is `scenario_unsupported` and carries a `proposedScenarioExtension`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

All three extend `Agent<TInput, TResult, TLoop>`. Callers use `.run(input)`.

### Recipe (template) data vs per-generation (instance) data

These two capabilities are deliberately distinct data shapes:

- **`scenario-data`** is per-subject **instance** data - the concrete rows a single
  generation's scenario instance _actually generated_ (`ScenarioInstance.generatedData`).
  The generation reviewer and healing use it to judge whether a
  subject's plan referenced data the scenario really seeded (a strong `agent_limitation` /
  `plan_mismatch` signal; healing gets it per failing subject so it can rewrite a plan to
  match the seed rather than report a bug).
- **`scenario-recipe`** is **recipe template** data - what each scenario is _designed to
  seed_, read from the point-in-time `ScenarioRecipeVersion.fixtureJson` for the snapshot.
  The diffs **analysis** agent uses it: analysis runs _before generation_, so no instance
  exists yet - the recipe is the only artifact describing each scenario's data. Field values
  may still be unresolved variable placeholders (e.g. `{{testRunId}}`).

Both resolve their payload at setup (the only DB-touching step), inline a bounded summary,
and disclose full records on demand via an in-memory tool, keeping the agent run DB-free.

Each agent's directory contains: the `Agent` subclass, a `Loop` subclass that implements the capability interfaces the agent's tools depend on, the per-agent action/result tools, and the prompt source.

## Adding a new tool

1. Decide which capability interface(s) the tool reads off the loop. If it needs the codebase, type it against `CodebaseLoop`; if it needs the test list, `TestLookupLoop`; etc.
2. Create a file under `agents/tools/<category>/<name>-tool.ts` that exports a class extending `AgentTool<TInput, TOutput, TLoop>`.
3. Register the tool in the relevant agent's constructor (or in multiple agents if it's shared).

For action tools, push to the loop's public mutable fields directly (`loop.affectedTests.push(...)`); for cross-tool invariants, either inline the check or extract a free helper alongside the tool. The loop subclasses expose their state as `public readonly` fields - there is no separate "collector" abstraction.

## Bash tool

The `bash` tool (`agents/tools/codebase/bash-tool.ts`) lets the research agents run shell commands against the clone. It runs each command with `sh -c`, with the working directory pinned to the clone root and a scrubbed environment (`buildSafeEnv` passes only `PATH`/`HOME`/`LANG`, so worker secrets never reach the child), a 30s timeout, and head+tail output truncation.

**There is no process isolation.** The command allowlist + grammar validator (`validateCommand`) and the scrubbed environment are the only gates. The allowlist is a first gate and ergonomic guidance, **not** a security boundary: several allowed verbs (`find -exec`, `sed -i`, `awk 'system()'`, `git` write subcommands) can write, execute, or reach the network within a single validated invocation. The tool therefore trusts its own agent and runs against the user's own clone; the residual risk (writes to the worker filesystem, network egress, host-path reads outside the clone) is accepted.

> This previously wrapped the child in [bubblewrap](https://github.com/containers/bubblewrap) (`bwrap`) for full process isolation, but `bwrap` requires unprivileged user namespaces that are blocked on the worker nodes (every command failed with `Creating new namespace failed: Operation not permitted`), so the isolation was removed. If isolation is wanted back without userns, prefer pod-level controls (a `NetworkPolicy` denying egress + a read-only root filesystem `securityContext`).

## Adding a new agent

1. Create `Loop` subclass that `extends AgentLoop<TResult>` and `implements` the capability interfaces the agent's tools need.
2. Create `Agent` subclass that `extends Agent<TInput, TResult, TLoop>`. Implement `buildUserPrompt(input)` and `createLoop(input)`. Construct all tools as `private readonly` fields in the constructor.
3. If the agent has a finish tool that needs to merge collector state into the result, extend `ReportResultTool<TInput, TResult, TLoop>` and implement `buildResult(input, loop)`. Otherwise use `FinishTool<TResult>` directly.

## Error handling

Tools classify their failures explicitly:

- **Bad input the model can retry** → throw `FixableToolError` with an optional `suggestFix()` message.
- **Operation didn't succeed but the tool ran fine** (bash exit ≠ 0, file not found, no grep matches) → return success-shaped data; let the model interpret it.
- **Infra failure** → throw `FatalToolError`; the loop terminates.
- **Anything else** → caught by the default `continue_unless_fatal` policy and surfaced to the model as a fixable failure.

## Entry points

`@autonoma/diffs` is a pure agent library: it ships the `GenerationReviewer` agent class and the loader interfaces it consumes (`ScreenshotLoader`, `VideoDownloader`), plus the prompt-building blocks (`buildGenerationReviewMessages`). The mp4 is produced upstream at record time by the engine (see `apps/engine-web/src/platform/optimize-recording.ts`), not here, so `packages/diffs` stays dep-light: `tryUploadVideo` only downloads whichever key it is given.

## `./analysis` - the merged analysis pipeline library

`src/analysis/` is a **copy** of the classifier (the `ClassifierAgent` + its vision probes + its tools: read-only `bash` / `prior_runs` / `analyze_video` / `view_step_details`, plus the live-backend tools `run_script` / `get_preview_env` / `get_app_logs`), re-homed out of `packages/investigation` (issue #1599). It is the home of the merged analysis pipeline - Impact Analysis -> Investigators (parallel) -> Reporter -> authoritative settlement - which runs on the **diffs worker** (`TaskQueue.DIFFS`). It has a single behavior: the pipeline IS the PR analysis, running on the branch's real pending snapshot, settling it as active on success or failed/cancelled on a terminal non-success outcome, and filing NO `Bug`/`Issue` (its per-snapshot `AnalysisFinding`s + branch-scoped `AnalysisIssue`s are the store). It is the **only** PR-analysis pipeline - there is no env switch, no per-org setting, and no diffs fallback to choose between; `DiffsRunPreparer` starts an analysis run for every PR run, full stop. Rolling it back means reverting, not flipping a flag.

The diffs pipeline it replaced is mid-retirement: nothing starts a diffs run or an investigation shadow any more, but their historical rows still render, and supersession still closes out a pre-cutover run whose pending snapshot would otherwise block its branch forever (a `diffsAnalysisWorkflow` was started without an execution timeout, so it never self-reaps). The workflows, activities and `packages/investigation` come out once Temporal reports no such executions left.

The classifier has **one** vision model (`src/analysis/ai/model-session.ts`): the probes and `analyze_video` both run on `smart-video` (MiniMax M3 via OpenRouter, overridable with `INVESTIGATION_VIDEO_MODEL`), which reads literal on-screen values - a `-$350` sign, a card colour - far more reliably than a general vision model. It also invents error states, which is why the prompt treats every scan as a finding to VERIFY rather than a verdict. Frames never go through a vision model at all: the final screenshot is attached to the prompt and `view_step_details` returns raw pixels, so the reasoning model reads them itself. OpenRouter rejects webm, so the classify activity transcodes a pre-optimizer webm recording to mp4 before handing it over.

Investigation's **selection** was deliberately NOT carried over (the copied selector is dead-on-arrival - #1510 replaces Impact Analysis with the `DiffsAgent`/`runDiffsAnalysis`, and the epic rejects the carry-forward the old selector did). The classifier's live-backend tools are kept as-is; converting them to frozen-source reads (and removing `run_script`) is deferred to #1514.

On a **main-branch run**, Impact Analysis first hosts the **merge flow** (`apps/workers/diffs/src/analysis/merge-flow.ts`, over the deterministic `classifyTestsForMerge` + `detectRelevantMerges` here in `packages/diffs`): it enumerates the PRs merged since main's last analyzed head, pins each source branch's snapshot at the PR's head SHA, and 3-way-classifies every test against the merge base. A plan the branch changed while main stood still is **imported** (`UpdateTest`, or `ImportTest` for a test main does not assign yet - the same `TestCase`, never a second one); a test the branch deleted from an untouched main is **dropped** (`RemoveTest`); a delete the branch made to a test main has since edited resolves **modify-wins** (main keeps its plan); and a both-sides edit stays a **pre-classified conflict** the agent re-plans. Without this, main re-derives its suite from the raw diff and re-runs the very plan a merged PR self-healed - failing it, and reporting a false `client_bug`. Every edit goes through the update actions on the run's own snapshot, so an imported test lands in the draft the rest of the stage reads AND arrives with a queued generation, which is what makes it a real investigation target rather than a silent write. Imports are withheld from the agent's Existing Tests list (their plan is already settled), and a PR whose source snapshot cannot be pinned - like a range this shallow clone cannot connect base to head across - falls back to the agent re-deriving it from the diff, logged as a warning rather than silently.

Impact Analysis records what it did, because nothing downstream can recover from a bad selection and the stage decides which tests the run investigates at all: the DiffsAgent's full conversation lands at `diffs-job/{snapshotId}/analysis-conversation.json` and its model spend at `ai_cost_record` under the `analysis-impact` tag (alongside `analysis-reporter` and `investigation-classify`), both keyed on the run's snapshot (`apps/workers/diffs/src/analysis/run-diffs-agent.ts`). Both writes are best-effort - the selection is the stage's only irreplaceable output, so neither an S3 nor a DB failure may discard it. The transcript is the only evidence of *why* a run selected nothing: `AnalysisReport.impactReasoning` is display prose the agent wrote about itself, with no schema and no guarantee it agrees with the selection it describes.

Each **Investigator** (`packages/workflow/src/workflows/investigator.workflow.ts`) is a bounded state machine: it runs + classifies its test and resolves to one `AnalysisVerdict` (`passed` / `client_bug` / `engine_artifact` / `environment_failure` / `scenario_issue` / `plan_mismatch` / `invalid_test`). On a `plan_mismatch` (the app worked, the test's plan does not match it) it self-heals - rewrites the plan on its OWN `(snapshot, testCase)` rows and re-runs, at most once (N=2). `plan_mismatch` and `invalid_test` split the wrong-test space along recoverability. An exhausted `plan_mismatch` loop resolves back to a **kept** `plan_mismatch`: the Investigator does not remove a test it could not stabilize within budget, because that test may be salvageable in a later snapshot or may be surfacing a defect the classifier misdiagnosed. Any rewrite it applied is REVERTED first, so the plan that promotes is the one the test started with - a rewrite optimized to make the test pass can blunt the very assertion catching a real bug, and a plan we know still fails is never promoted. The revert repoints the assignment at the pre-rewrite `TestPlan` record rather than re-authoring its text, so the snapshot reads as genuinely unchanged for that test (both change computations key on `planId`). `invalid_test` is the deliberate, evidence-backed REMOVAL for an irreparable test (a feature that never existed, browser-unexecutable steps, a premise the app contradicts): it drops this snapshot's assignment via `RemoveTest` whatever the test's origin (destroying a proposed test's `TestCase` would cascade away the very rows that record why it was removed), reachable up front only when the impossibility is provable, else only on the final iteration after a failed heal. `selfHealAnalysisTest` / `revertSelfHealPlan` / `deleteAnalysisTest` (`apps/workers/diffs/src/activities/analysis`) apply these row-local writes. On a self-heal RE-RUN the second classify pass receives the prior pass's verdict (`priorPass` on `ClassifyInvestigationRunInput`) so it judges the corrected plan against that conclusion - a still-failing rewrite with no new defect evidence resolves back through the loop instead of flakily escalating to `client_bug`.

**Every iteration persists its own verdict**, before the loop acts on it: `persistAnalysisClassification` finds-or-creates the test's `AnalysisFinding` and APPENDS an `AnalysisClassification` carrying the classifier's full rich output (`AnalysisClassificationReport`: narrative, evidence, per-step run-trace frames, media keys, and the `conversationUrl` - a best-effort per-generation upload of the classifier's own LLM conversation), then repoints `AnalysisFinding.currentClassification` at it. One iteration never overwrites another, so the verdict that authored a self-heal rewrite - and the reasoning behind it - survives the pass that replaced it; a plan is never edited on the strength of a verdict that is not yet on disk. Which slot it lands on (`number`) comes from the Investigator's own iteration counter rather than a count of stored rows - the `RefinementLoop`/`RefinementIteration` convention - so re-filing an iteration restates its row instead of appending a duplicate that would read downstream as a self-heal that never happened. A crashed child's containment takes the slot past every real iteration. The finding itself holds only the per-test facts (`testCaseId`, `origin`, `selectionReason`, `issueId`) and is unique per `(job, testCase)`; readers resolve the run's verdict through `currentClassification`, which is what keeps a superseded iteration structurally uncountable. The parent contains a crashed child by appending an `engine_artifact` classification rather than overwriting what the child already wrote.

**Settlement** is the one terminal path: `settleAnalysisRun` first settles the snapshot, unfinished generations, and `AnalysisJob` together. A successful run promotes the snapshot; a failed run marks unfinished generations and the job failed; a superseded run cancels the pending snapshot. The snapshot transition is the mutex, so a racing terminal path returns without repeating GitHub effects. After durable settlement, `settleAnalysisGitHub` best-effort updates the merge gate and, only for a successful run, posts the PR comment. It does NOT derive or write the verdict - the Reporter authored the `AnalysisReport` (verdict + counts included) one stage earlier, from the very issues it reconciled. See the coverage-plane derivation in **The Reporter** below.

The per-test `AnalysisFinding` store (with its per-iteration `AnalysisClassification` children carrying each verdict's evidence + media keys + classifier-conversation key) is the single source of truth for every finding, `client_bug` included - the pipeline files no `Bug`/`Issue`. (The shared `resolveOrCreateBug` / `BugMatcher` stay exported for the healing `report_bug` path and are not called from analysis.)

### The classifier (`src/analysis/classify/`)

The **classifier** (`ClassifierAgent`) determines the true cause of ONE browser test run against the PR's preview app and commits to a single `RunVerdict`. It is an `Agent<ClassifierInput, RunVerdict, ClassifierAgentLoop>` on the same `@autonoma/ai` harness as every other agent here; `ClassifierInput` carries the static run facts, the `Codebase` handle + base/head SHAs, and the run-scoped capabilities the worker injects (`loadBaseline` / `loadAppLogs` / `preview`). The two models are fixed per instance on the constructor (`model` / `videoModel`).

**One loop, not two phases.** The four deterministic vision probes (error / fidelity / visual-sanity / mission) run pre-loop in `buildUserPrompt` - in parallel, 3-minute timeouts each, degrading to a note in the prompt on failure. They are deliberately _not_ tools: the model gets those four signals wrong when left to its own discretion.

**No recording, no scans.** Every probe asks what happened _across_ the run, which no other artifact answers, so a run that recorded nothing gets no probes and no `analyze_video` - the prompt renders one `NO RECORDING FOR THIS RUN` note in place of the four scan sections and says what is left to reason from. This is not a corner: ~48% of classifications have no recording, and 97% of those executed no steps either (the run died before or during startup), which is why they land on `engine_artifact` / `environment_failure` / `scenario_issue` and essentially never on `client_bug`. Rendering four empty scans under headers asserting "independent vision pass over the full video" - next to a `Set planFidelity from this scan` instruction - described an investigation that had not happened. The model then investigates with the tools and commits through the terminal `finish` tool (`VerdictTool`), with every tool result still in scope. That is the point of the shape: the verdict used to be a SECOND model call whose only context was the first call's prose, so evidence reached the verdict only if the model had thought to restate it. `toolChoice: "required"` + the finish tool are the loop's stop; there is no `maxSteps` knob - it inherits `DEFAULT_MAX_STEPS`, the harness's runaway backstop (the old 60-step cap was measured firing 4 times in 17,602 classifications). On exhaustion `MaxStepsReached` propagates and the Investigator contains the test as a coverage-plane `engine_artifact` - there is deliberately **no fallback verdict path**.

`VerdictTool` is gate-free by design: it normalizes `VerdictForModel` into the discriminated `RunVerdict` via `toRunVerdict` and nothing else. Zod is the only contract - verdict discipline lives in the prompt, where it can explain itself, because a structural gate would only teach the model to satisfy the gate.

**Output bounding** is per-tool, not cumulative: each tool declares a module-level char budget, advertises it in its own description, and truncates head+tail through the shared `truncateOutput`, whose marker carries that tool's own "how to ask for less" hint. Accumulation across steps is the loop compactor's job (`RedactOldToolResults(2)` above 700k input tokens, same as the Reporter and `HealingAgent`).

**Errors are typed, and never fatal.** The classifier's contract is degrade-and-disclose, so it throws `FixableToolError` liberally and `FatalToolError` nowhere. Every distinct failure is its own named, file-local subclass beside the tool that raises it - `VideoReadFailedError`, `AppLogsUnreadableError`, `PriorRunsUnreadableError` - carrying the fact in its message and the way forward in `suggestFix()` ("ask one narrower question about a specific moment; if that fails too, fall back to `view_step_details` rather than re-reading the whole recording"). That guidance is what a stringly-typed `could not read X: ...` result never carries. A tool only ever raises its failed-read error: an absent capability produces no tool at all, so there is no unavailable-capability branch to reclassify on the way out.

The line between an error and a result is **"no answer" vs "an answer you did not want"**. An empty diff, an empty env list, and a non-zero `bash` exit are real findings the prompt reasons _from_ - the empty diff is how it rules out attribution - so they stay results, spelled out rather than left as a bare `(no changes)`. Absent media (no recording, no final frame, no step frames) and an out-of-range step number are not findings; they are the tool declining to answer, so they go through the error channel. Do not hand-roll an `{ ok: false, reason }` payload for those: `AgentTool` already wraps every result in a success/failure envelope, and nesting a second one inside it yields a `{"success":true,"result":{"analyzed":false}}` the model has to notice for itself.

**The trace is the index; `view_step_details` is the drill-down.** Each trace line is capped so a 120-step run still fits, and carries what the step targeted, an `assert`'s individual assertions with whether each held, and an offset from run start (so a scan's "after the 2nd message" and a `get_app_logs` line over the same window both pin to a step). `view_step_details` then discloses ONE step with nothing truncated: BOTH frames as pixels plus the engine's own record (interaction, params, structured output, error) - a step the model bothered to ask about is one whose assertion breakdown or error payload is worth reading whole.

`RunArtifacts.inspectableSteps` carries storage KEYS, not bytes: a run has up to 120 steps and a classification drills into two or three, so frames rehydrate through the injected `ScreenshotLoader` on demand. It matches the attempt's `order` - the number the prompt's trace actually renders - never an array index, which would silently return the wrong step whenever orders are not a contiguous 1..N. Only the before-frame is annotated with the resolved click point: it is the state the click was resolved against, so it is the only one where the marker means anything.

> This tool was dead in production until #1906: `buildRunArtifacts` hardcoded its step list to `[]`, so every call returned an inert "no per-step screenshots" string - while the system prompt repeatedly pushed the model at it ("on the LATER steps ... and trust those frames"). The keys were already being read for the run trace; they were just never handed to the classifier.

`bash` (the shared read-only shell tool) replaced the old `read_code` / `grep_code`, and then `git_diff` too. That tool justified itself on two things the model supposedly could not reproduce from the shell - the `baseSha..headSha` range and the lockfile/build-noise exclusion pathspecs - and neither survived contact: `git` is in the bash allowlist, so the range was knowledge we had simply declined to hand over (it is in the prompt now), and the exclusions filtered the patch SILENTLY, which is how a `**/`-prefixed pathspec quietly failed to match root-level lockfiles for months. The diff stat is already in the prompt, so the model knows what changed before it reads anything and can scope its own `git diff`. `src/pr-range.ts` remains for Impact Analysis and the prompt's diff stat.

The persisted conversation is `[user(promptText), ...loopConversation]`, via a `buildTranscript` override. The prepend is load-bearing, not nostalgia: the four probe outputs are non-deterministic generations that exist ONLY in that prompt and are usually the key artifact when debugging a bad verdict. It hangs off `buildTranscript` rather than wrapping `runLoop` precisely so it applies when the run FAILS too - a classification that died is the one whose probes someone will want to read. Media parts are dropped - the run screenshot rides on the finding as a signed key.

### The Reporter (`src/analysis/report/`)

The **Reporter** (`ReporterAgent`) is the reconcile stage and **authors the `AnalysisReport`** - the row is born here and nowhere else, so its existence means the Reporter ran (a Reporter failure fails the run, leaving no report). Given a job's findings plus the branch's evolving issues and prior reports, it reconciles them into de-duped, **branch-scoped** `AnalysisIssue`s (a problem that persists across snapshots, above the per-snapshot `AnalysisFinding`), backfills each finding's `issueId`, derives the run's verdict + counts, and writes the holistic PR report prose (`AnalysisReport.reportMarkdown`) plus a one-paragraph `summary` - all in one transaction, so the report, its verdict, and its issues are always consistent.

It authors prose for **two shapes of reader**. `reportMarkdown` is the document rendered on a web page that resolves the inline `evidence:`/`issue:`/`finding:` tokens; `summary` is the same verdict in 1-3 plain sentences for the surfaces that render neither Markdown blocks nor those tokens - the GitHub PR comment body and the PR page's verdict subtitle. `summary` is flattened at persist (`toPlainSummary`: images removed, links unwrapped to their text, headings and newlines collapsed) rather than trusted to follow the prompt.

Each issue also designates a **primary test**: which one of its covered tests reproduces the problem most clearly. Which _test_ is a judgement call, so the agent makes it (naming a slug, validated to be one of the same call's `findingSlugs` and resolved to the `primaryTestCaseId` FK at persist); which _run_ of that test to feature is mechanical, so readers resolve the newest covering finding for that test. That split is what lets a carried-forward issue's clip and "watch the run" deep-link track the PR's current head with no re-designation.

The **verdict + counts are DETERMINISTIC, in code, never by a model** (`summarizeVerdictPlanes` + `deriveReportHeader`): the `AnalysisVerdict` taxonomy is partitioned programmatically into an **app-health** plane (`client_bug` / `passed` - the PR headline) and a **coverage-confidence** plane (`engine_artifact` / `environment_failure` / `scenario_issue` / `plan_mismatch` / `invalid_test` - never a bug, never blocking), and the coverage plane is summarized per category (including the kept `plan_mismatch` tests the run could not stabilize but left in the suite, and the removed `invalid_test` ones). The **verdict + bug count are issue-derived**: the PR is red iff the branch has any OPEN bug-kind `AnalysisIssue` (so a bug carried across snapshots keeps it red even when no test re-ran it, and resolving flips it green). `AnalysisReport.clientBugCount`/`verdict` - which the PR-list pill, checkpoint rail, GitHub check, and comment read - are written at report birth. The stage runs in `runReporter` (`apps/workers/diffs/src/activities/analysis`).

The Reporter is built on the `@autonoma/ai` **AgentLoop** harness, like every other agent in this package. A per-run `ReporterAgentLoop` holds the minted-evidence allow-list; the terminal `finish` tool enforces three structural **coverage guarantees** as fixable-retry tool errors (every live `client_bug` finding is covered by an issue; every open issue whose covering test re-ran and passed is resolved; every open issue whose covering test still failed is carried forward) and **grounds** every authored surface at persist time - unbacked `evidence:<assetId>` images are stripped, `suspectedCause` file:line references are validated against the checked-out repo (a fabricated one is dropped), and a hero screenshot resolves only from a fetched asset. The fixed-schema tools are `fetch_evidence` (mints grounded evidence tokens as inline vision), `read_scenario` (a recipe on demand), read-only `bash` (diff/code, reused from the shared codebase tools), and the three reconciliation tools `open_issue` / `carry_forward_issue` (re-confirm, and the reopen path) / `resolve_issue`. It runs on a `reporter` model capability key (native OpenAI, vision + strong reasoning). The schema is `AnalysisIssue` (branch-scoped, incl. `primaryTestCaseId`), `AnalysisFinding.issueId`, and `AnalysisReport.reportMarkdown` + `summary` + `evidenceManifest`; findings key on the run's `AnalysisJob` (shared snapshot PK), which exists from the start of the run, so an Investigator persists during fan-out and the Reporter authors the report over those findings afterward. An issue's covered set is DERIVED from the findings attributed to it, not stored: `issueId` is the one record of coverage, so it cannot drift from a parallel list of slugs.

### The analysis PR comment

`settleAnalysisGitHub` (`apps/workers/diffs/src/activities/analysis`) invokes `postAnalysisComment` through the shared comment system after a successful, durable run, gated by `ANALYSIS_PR_COMMENT_ENABLED` (on by default; set false to keep the pipeline running while it stops touching GitHub). The comment is **issues-first**: the cards are the branch's OPEN bug issues, not this snapshot's findings, so a bug carried across snapshots keeps its card and each one deep-links to the stable PR-level issue-detail page. Its two links mean different things - the title goes to the ISSUE, the media and "Watch replay" go to the ONE RUN the issue's primary test designated (the animated clip is preferred over the issue's hero frame, since GitHub does not render the hero's pin). The card **diagnoses** rather than prescribes: a "Suspected cause" line plus a nested Evidence collapsible built from the repo-validated `codeReferences`, and no fix instructions.

Fix guidance lives in the **coding-agent handoff** instead - a paste-ready brief in a copy block plus prefilled "open in Claude Code / ChatGPT / Cursor" deep-links, so the reader's own agent decides what to change with the grounded evidence in hand. The prompt's URL plumbing is shared with the investigation comment via `@autonoma/github/comment` (`buildAgentHandoffLinks` / `capHandoffPrompt`), because the encoding rules are vendor quirks - Cursor truncates its `text` param at the first `&`, and unescaped parens break the markdown link the href sits in. The prompt also points the agent at the MCP tool `get_analysis` (`apps/api/src/mcp/debug-mcp-server.ts`, backed by `BranchesService.getAnalysisForPr`), which serves the same issues live and without a login - so an agent can act on a re-run's current issue set rather than the snapshot this comment rendered. Both build their in-app links from the shared builders in `@autonoma/types` (`app-links.ts`), so a route change cannot leave one of them pointing at a dead page.

The read is `loadAnalysisCommentInput`, kept separate from the posting activity so the issue → designated-run join is covered by an integration test against a real database.

The copied classifier still emits its 7-value `Category` and a `planFidelity` field, both untouched here: the taxonomy is resolved by a mapping layer (`routeVerdict`) rather than editing the classifier, and fidelity is derived from whether the test was classified more than once rather than consuming `planFidelity` - which is now vestigial for the merged pipeline. Teaching the copied classifier to emit the taxonomy natively and dropping `planFidelity` is deferred to the classifier-cleanup slice (#1514).

After the re-home the pipeline shares no code with the frozen `packages/investigation`, so every downstream analysis-merge change modifies this copy freely. It is exposed on a dedicated subpath because it ships its own `openModelSession`/`ModelSession` that would collide with the diffs agents' model session on the main entrypoint. The pipeline's Temporal activities + worker infra live in `apps/workers/diffs/src/activities/{analysis,classify-run}`.
